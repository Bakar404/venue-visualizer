# User test, session 1 (2026-11-21)

**Who:** the project owner planning a real wedding at a real venue, using the live app (Claude Code brain + Copilot image
engine) at http://localhost:3000.
**Evidence:** the local SQLite records (chat messages, jobs, looks, imports) plus screenshots taken while reproducing.
Quoted user messages are verbatim, typos included.

## What the user tried

1. **Found their venue by name.** Research returned 6 spaces and 7 photo links. On import, every photo became a
   *reference* (the "I'm using these for personal planning" box was not ticked), so all 3 imported spaces had **no base
   photo**. The user left that venue and continued in another one.
2. **Designed by chat** in the Grand Ballroom: 9 turns in 4 minutes.
3. **Rendered** a "moody night" Look, which got a "May have altered the room" badge.

## Findings → fixes → acceptance tests

Each finding becomes a failing test first (proof of the bug, saved to `docs/proof/<id>-red.txt`). Then it is fixed
and the same test passes (`docs/proof/<id>-green.txt`, plus screenshots for UI items).

| ID | What happened (evidence) | Severity | Fix | Acceptance test |
|----|--------------------------|----------|-----|-----------------|
| UT1 | Chat grows the whole page: 9 turns made the Studio 3,082 px tall in a 900 px window. The message box and **Render** button were pushed off-screen. | High | Studio fills the viewport (`100dvh`). The chat history scrolls inside its own panel with a visible scrollbar, and the composer and Render bar stay pinned. Auto-scroll to the newest message only if the user is already at the bottom; otherwise show "↓ New message". | e2e: after 12 long messages, `document.scrollHeight <= innerHeight`. The chat list is scrollable, and the composer and Render button are in the viewport. If the user scrolled up, a new reply doesn't move them. |
| UT2 | The user expected the chat to render: *"i dont see the new photos rendered"*, *"i want to redner a new photo to see how the room looks when its dark outside"*, *"mix, i want to see it first"*. The agent answered that it can't render. | High | Chat responses carry an `intent` (`edit`, `render`, `question`, `none`). For `render` (or edit + "see it"), the reply shows an inline **Render now** card (engine, ~time, uses credits) that starts the render with one click. Any reply that changed the spec gets a quieter "Render this change" action. | API: "show me how it looks" → `intent: "render"`. e2e: a chat asking to see it shows the card, and clicking it queues a render job for the current plan. |
| UT3 | A quick-reply chip sent the *question itself* as the user's message: *"Do you want to keep the moody dim lighting with cool blue uplighting…?"* | High | Ambiguities become `{question, options[]}`. The question is shown as text and only the **options** are chips. | e2e: clicking a chip sends the option text, never the question. Schema test for the new shape. |
| UT4 | There was no way to say time of day: *"make the time 7pm so its dark out"*, *"make the room dakr"*, *"i mean that its not daylight outside"*. It took 3 turns and ended up in free-text notes. | Medium | New `DesignSpec.scene` = `{time_of_day: daylight\|golden_hour\|evening\|night, windows: as_photographed\|dark\|sheer_draped}`. The brain maps "7pm/dark out/not daylight" to it, and prompts render it explicitly. Shown in the spec form. | Pipeline: the mock brain plus prompt tests. "make it 7pm so it's dark out" → `scene.time_of_day = "night"`, `windows = "dark"`, and the prompt mentions night and dark windows. |
| UT5 | The moody burgundy/plum/blue design was saved as **"Ivory, gold & sage green"**, because the name comes from the first 3 palette colors and the old colors stay first. | Medium | The brain returns a short `look_name` ("Moody night, blue uplighting"). The web uses it for new Looks and falls back to the newest palette colors. | Unit: the name reflects the latest patch. e2e: Save as Look prefills the brain's name. |
| UT6 | Import dead end: every web photo silently became a reference, spaces had no base photo, and the user abandoned the venue. | High | (a) Import review: if any photo is marked "Use as base photo" but the confirmation box is unticked, the Import button explains why and focuses the box. (b) Studio for a space with references only: show them with **Use as my base photo** (inline confirm → server downloads it) and **Generate an empty base view from this**, plus the upload, video and describe options. | e2e (mock): import with an unticked box can't silently drop bases. A references-only space shows the reference photos and actions, and "Use as my base photo" creates an approved base. API: `POST /api/spaces/{id}/references/import`. |
| UT7 | The night render showed "May have altered the room". The architecture is intact, but heavy relighting failed alignment (a known limit). The badge doesn't say why or what to do. | Low | The badge shows the backend's `structure.reason` in plain words ("Lighting changed a lot, so we couldn't confirm the room matches. Compare with the slider."). It distinguishes "couldn't verify" from "changed". | Unit: reason mapping. e2e: the badge tooltip text. |
| UT8 | After chatting, the canvas still showed an older render from a different plan, and the user thought nothing had happened. | Medium | When the current plan differs from the plan of the displayed render, show a banner over the canvas: "Your plan changed since this render. **Render to see it**". | e2e: change the spec via chat → the banner is visible → render → the banner is gone. |

## Out of scope for this round
- A true night re-light that keeps alignment (it needs a relighting-aware check). For now it's documented as a known limit.
